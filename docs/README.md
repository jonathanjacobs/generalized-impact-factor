Project definition, data-handling and third-party terms, and testing evidence for `generalized-impact-factor`. Each document below has its own `Audience` / `Use this when` header — start with `DESIGN.md` if you're new to the project.

| Document | Question it answers |
| --- | --- |

| [REQUIREMENTS.md](REQUIREMENTS.md) | What must be true before the result is acceptable? |
| [CODE_STYLE.md](CODE_STYLE.md) | What does readable Python look like here, and what do the automated checks cover? |
| [DATA_GOVERNANCE.md](DATA_GOVERNANCE.md) | What may go in Git, and what may not? |
| [THIRD_PARTY.md](THIRD_PARTY.md) | Which outside tools, APIs, and packages does this depend on, and on what terms? |
| [TESTING.md](TESTING.md) | What evidence shows this works, and what hasn't been checked yet? |
| [history/VALIDATION_HISTORY.md](history/VALIDATION_HISTORY.md) | What has been validated, when, and by whom? |

This project has not adopted every document `atcc-dev-template` offers (e.g. `ARCHITECTURE.md`, `adr/`, `investigations/`, `RUN_PROVENANCE.md`, `TEAM_ROLES.md`) — see the "Trim unused template scaffolding" reasoning in the project's history for why, and add one if a real gap starts costing someone time.
